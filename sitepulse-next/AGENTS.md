# SitePulse AI Assistant Instructions

Welcome to the SitePulse codebase. Please follow these architectural rules strictly to maintain the integrity of the application.

## 0. How to communicate with me (the user)
The user is the product owner, not a trained developer. When responding:
- **Lead with a 1-2 sentence plain-English summary** of what you did or found, before any technical detail.
- **Explain jargon in passing** — e.g. "the mutation queue (the list of offline changes waiting to save)".
- **Keep it short.** Prefer a few sentences over long essays. Only go deep when I ask, or when a decision genuinely needs it.
- **Still be precise** — don't dumb down the actual technical work or hide trade-offs; just frame them in everyday terms.
- When suggesting a change, say **what it does for the app/user**, not only how the code works.

## 1. Core Architecture
- **Framework:** Next.js (App Router)
- **Styling:** Tailwind CSS v4, Lucide React for icons
- **State Management:** Zustand (for Global UI / Persisted Settings — modularized into `useMapStore`, `useUIStore`, and `useSettingsStore`)

## 2. State Management & Data Fetching (CRITICAL)
- **NEVER** use `useState` or `useEffect` for fetching database data or managing global UI state.
- **Data Fetching:** Always use/extend the established TanStack Query custom hooks (`src/hooks/useProjectQueries.ts`, `src/hooks/useMapActions.ts`, `src/hooks/useProjectActions.ts`). Server state handles an **Offline-First** setup utilizing `@tanstack/react-query-persist-client` writing to `IndexedDB` for durable disconnected mutations. Do not break this mutation queue or the WebSocket cache injections that resolve Thundering Herds.
- **Global State:** All floating UI state (modals, active tools, selected units, filters) MUST be managed in the appropriate Zustand store (`src/store/useMapStore.ts`, `src/store/useUIStore.ts`, or `src/store/useSettingsStore.ts`).
- **Persisted State:** When accessing persisted Zustand properties (like `settings`, `mapSettings`, `legendPosition`), you MUST use the `useHydratedStore` custom hook (exported from `src/store/useSettingsStore.ts`) to prevent React hydration mismatch errors.
- **View navigation is URL-first (`?view=<mode>` — Polish Batch 1):** the project page's active view is owned by the `?view=` query param. `navigateToView(mode)` in `project/[projectId]/page.tsx` pushes the param (so Back walks views) AND mirrors it into `useUIStore.viewMode` (kept only as the in-memory read mirror) + `setToolMode('pan')`. Never switch views with a bare `setViewMode` — thread `navigateToView` down as a prop (TopHeader, ProjectDashboard, SettingsMenu already do). The canonical view list + first-load precedence resolver are pure `src/utils/viewRouting.ts` (tested). Phones navigate via the bottom tab bar (`src/components/MobileViewTabBar.tsx`, Nav plan Phase 4 — Polish Batch 3): the `MOBILE_VIEWS` four (List/Map/Look-Ahead/Dashboard; Schedule intentionally absent at phone width), driving `navigateToView`, mounted as the last flex child of the project page's 100dvh column so it can't overlap the swipe deck. The page passes `mobileAllowed: MOBILE_VIEWS`, so a phone's saved default view sticks unless it's Schedule (clamps to List); a valid `?view=` deep link always wins, even for Schedule. `viewMode` never enters TanStack Query.
- **The header is context-aware (Nav plan Phase 3 — Polish Batch 2):** TopHeader's Level selector, Scope tabs, Activities button, and Export are gated by `controlVisibility(viewMode)` in `src/utils/viewRouting.ts` — an owner-locked per-view matrix pinned by table-driven tests. To change which view shows which control, edit that matrix (and its test); never ad-hoc hide header controls in JSX. Export additionally keeps its `activeSheet?.base_image_url` gate. On the Dashboard the Scope tabs list **project-level tracks** (`projectTracks`, deduped from `activities[].track` in page.tsx and threaded down) instead of `activeSheet.active_scopes`, and the page's trackingMode clamp targets the project track set while on the Dashboard so it can't clobber a project-level pick — every other view clamps to the sheet's scopes as before.
- **Theme is applied once, at the root:** the Light/Dark/System setting is wired to `<html data-theme>` by `src/components/ThemeApplier.tsx`, mounted in `src/app/layout.js` (`'system'` follows `prefers-color-scheme` live). Do NOT re-add per-page `data-theme` effects; only `data-theme="dark"` is meaningful in `globals.css` (absence = light).
- **`pendingChanges` is intentionally local `useState`** in `useFieldData.ts` — do NOT migrate it to Zustand or TanStack Query cache. It is a staging buffer that feeds the IDB mutation queue via `handleApplyAll` → `onApplyPendingChanges` → `commitUnitActivity`. Moving it to global state would bypass the offline replay queue. However, an **IndexedDB persistence layer** (`src/utils/pendingChangesStore.ts`) writes the in-memory state to IDB on every update and rehydrates it on mount, so pending changes survive page refreshes and tab closures. IDB keys are **project-scoped** (`sitepulse-pending-changes-${projectId}`) to prevent cross-project data contamination. A `hasRehydrated` guard prevents the persist effects from overwriting IDB with empty state before rehydration completes.
- **Idempotent Sync Engine (`status_logs`):** The `status_logs` table has a `UNIQUE(unit_id, activity_id)` constraint enforcing one current-state row per slot. All writes use either the `upsert_status_log` RPC (single mutations, `log_data.activity_id`) or `.upsert({ onConflict: 'unit_id,activity_id' })` (bulk). A Last-Write-Wins timestamp guard in the RPC rejects stale `client_timestamp` values. **Never revert to plain `.insert()` for status_logs** — it will cause constraint violations. **Slot key is `activity_id`, not the activity name** (Scheduling Foundation Slice A, Phase 1 — `20260701_activity_model.sql`): `status_logs` FKs `activity_id → activities(id)`; the read hooks join `activities(name)` and synthesize a display-only `activityName` onto each `StatusLog` (so the app still correlates/displays by name), while writes carry `activity_id`. Strip that synthesized `activityName` before any `status_logs` write (the write paths also strip the legacy pre-rename `milestone` key), and never re-add a name column or a name-keyed slot constraint.
- **Status Audit Log:** A trigger-managed `status_audit_log` table records every state change (append-only). History/timeline queries (`useUnitHistory`, `useStatusHistory`) read from `status_audit_log`, NOT from `status_logs`. `status_logs` is current-state only; `status_audit_log` is the full timeline.
- **Per-Item IDB Checkpoint:** `handleApplyAll` dequeues items individually from IndexedDB after each successful mutation. An `isSyncingRef` guards the reactive `useEffect` persist hooks from firing during the sync loop. If the app crashes mid-sync, only unsynced items remain in IDB on rehydration. Do NOT remove `isSyncingRef` or revert to all-or-nothing queue clearing.
- **Capture-Time Timestamps:** `client_timestamp` is stamped at offline-capture time (when `PendingChange.capturedAt` is set in `handleLocalUpdate`), NOT at sync time. This ensures history timelines reflect actual field work progression. The `commitUnitActivity` function in `useMapActions.ts` passes `extraProps.client_timestamp` through to the mutation; for immediate (online) mutations, `useUpdateStatus` stamps it as a fallback.
- **RLS Security Posture (2026-06):** `upsert_status_log` is `SECURITY INVOKER` — the `status_logs` RLS membership policies govern writes. Do NOT flip it back to `SECURITY DEFINER` or re-grant `EXECUTE` to `anon`; that re-opens unauthenticated status writes. Privileged-role checks in policies use `role in ('owner','admin','pm')` — `create_new_project` assigns `'owner'`, so never drop it from those lists. The `floorplans` storage bucket is **public by design** (capability URLs keyed by sheet UUID; required by the versioned-URL caching pipeline in §5) — revisit before handling sensitive drawings or multi-tenant launch.

## 3. Map & Canvas Engine (React-Konva)
- The interactive floorplan map is rendered via `<FloorplanCanvas />`. Operations rely heavily on Konva's drawing lifecycle.
- **Event Bubbling & Native Isolation:** Map interactions are complex. While React's synthetic `e.stopPropagation()` stops bubbling within the React tree (sufficient for most `onClick` events), it **does not** stop native events from reaching Konva's native DOM listeners. For custom HTML overlays that scroll or require strict isolation from map zooming/panning, you MUST use a `useRef` to attach a native DOM event listener (e.g., `el.addEventListener('wheel', (e) => e.stopPropagation(), { passive: false })`) and utilize CSS like `overscroll-contain` to prevent browser scroll chaining.
- The Canvas UI is modularized (`CanvasContextMenu`, `MapHorizontalToolbar`). Avoid bloating the main `FloorplanCanvas` file — it is a thin coordinator (Slice 2 decomposition): its logic lives in `src/hooks/useCanvas*`/`useTraceTool`/`useStampTool`/`useMeasureTools`/`useGeometryGestures` + pure `src/utils/canvasLayout|canvasRecolor`, and its three Konva layers mount via `CanvasBaseLayer` / `CanvasUnitsLayer` / `CanvasOverlayLayer` (`src/components/canvas/`; base → units → overlay order and the overlay `layerRef` feed the loupe — keep both). New canvas features extend a hook or layer component, not the coordinator.
- The field list UI uses a **Container/Presenter pattern**: `FieldStatusTable` (container, `src/components/FieldStatusTable.tsx`) invokes `useFieldData` (`src/hooks/useFieldData.ts`) for shared business logic, then renders one of two presenters: `StatusTable` (desktop table) or `MobileSwipeDeck` (mobile swipe). (`DesktopCardGrid` was removed — it duplicated `StatusTable` at lower density; do not reintroduce a third presenter without a distinct job.) `MobileSwipeDeck` is **lazy-loaded** via `next/dynamic` with `ssr: false` to exclude it from the desktop bundle. Shared UI atoms live in `src/components/ui/FieldStatusAtoms.tsx`. The mobile header includes a `SyncIndicator` (`src/components/ui/SyncIndicator.tsx`) that shows pending/synced state.
  - **Expanded-row audit fetching is viewport-gated (List View Performance — Phase 2):** an expanded location mounts `ExpandedActivityAudit` (`src/components/manage/ExpandedActivityAudit.tsx`), which runs a per-location `useUnitHistory` query — so "expand all" on a big list would otherwise fire N history requests at once and freeze the tab. `StatusTable` observes each expanded location's `<tbody>` via `useViewportPresence` (`src/hooks/useViewportPresence.ts` — one shared native `IntersectionObserver`, `root: null` + `rootMargin`) and passes `enabled={near-viewport}` down to `useUnitHistory(unitId, enabled)`, so only on/near-screen expansions actually fetch. Invariant: keep the **fail-open** degrade — when `IntersectionObserver` is unavailable (`supported === false`) callers MUST treat every row as near, so audits fall back to "always fetch", never "never fetch". A disabled audit shows the same state as "audit still loading" (entered actual-start only); it never changes what an expanded row renders. Phase 4 virtualization generalizes this — don't un-gate it.
  - **List rows are memoized (`src/components/manage/LocationRow.tsx`, List View Performance — Phase 3):** each location's `<tbody>` block (parent grid row + its expanded per-activity children incl. the viewport-gated `ExpandedActivityAudit`) is a `React.memo` component, so an edit re-renders only the row it touched instead of the whole table. For the memo to hold, `StatusTable` MUST feed each row **per-row primitives + this unit's slices** — `pendingChange = pendingChanges[unit.id]`, a per-unit `pendingTimelineForUnit` slice, `isSelected`/`isExpanded`/`isSaving`, and the Phase-2 `auditEnabled` boolean — **never** the shared `pendingChanges`/`pendingTimelineChanges`/`selectedUnitIds`/`nearIds` objects (their identity changes on every edit/scroll and would re-render all rows). Page/container callbacks are made referentially stable via `useStableCallback` (a latest-ref wrapper in `StatusTable.tsx`); the two edit handlers (`handleLocalUpdate`/`handleTimelineUpdate`) are stabilized at the source with `useCallback` in `useFieldData.ts` (empty deps — both go through the functional setter + stamp `capturedAt` at call-time, so they never close over the pending maps). `LocationRow` is presentation only (no store access); the memo is pinned by `StatusTable.memo.test.tsx`. Phase 4 virtualization recycles these memoized rows.
- **Schedule-variance analytics (`src/utils/progressAnalytics.ts`)** is the single source of truth for lag math: per-unit bottleneck variance (`computeUnitVariance`), the variance color/label encoding (`varianceFill`/`varianceLabel`/`VARIANCE_LEGEND`), and group rollups with pace + median-pace forecasts (`summarizeGroup`). Consumers: map Lag Mode, `HoverHistoryTooltip`, `UnitHistoryModal` (Journey tab), and the dashboard's `FloorPulse`/`TypeScorecard` modules. Do not fork this math in components.
  - **Applicability (N/A) is respected, same as the rest of the app (§2 applicability):** `summarizeGroup` takes `units` + an optional `ApplicabilityIndex` and counts only applicable (unit × activity) slots; `computeUnitVariance` takes an already-filtered activity list, so callers must pass `applicableActivities(trackActivities, unit, index)`. Never feed the raw track-activity list when an index is available — N/A slots would re-enter denominators and could become a false bottleneck.
- **Forecast confidence bands + Risk Radar (`src/utils/monteCarloForecast.ts` — Schedule That Thinks)** are an ADDITIVE layer beside `progressAnalytics`, never a fork of it — same extend-never-fork rule. A bootstrap Monte Carlo (`simulateFinishBand`/`bandForRollup` → `ForecastBand`) resamples a scope's OWN recent weekly pace to put an honest 80% range on each projected finish (hero card + `FloorPulse` rows); `activityRisk` ranks the activities whose P90 finish runs latest past their planned finish (the dashboard's `RiskRadar` module); `bestPaceMove` surfaces the single cross-level pace transplant that pulls the project finish in the most. It DELEGATES suppression to `projectForecastDate` for exact parity (a suppressed point forecast never gains a band), is deterministic (fixed `FORECAST_BAND_SEED` + `today` passed in — no `Date.now()`/`Math.random()`), and reuses `summarizeGroup` per activity/level. Extend this file for new forecast-uncertainty surfaces; leave the point-forecast math in `progressAnalytics` and `VARIANCE_COLORS` untouched.
- **One status-color language (`src/utils/statusColors.ts` — UI Polish P2, Polish Batch 3):** every chrome surface that colors a location's temporal state reads THE canonical palette from this module — none=slate, planned=AMBER, ongoing=BLUE, completed=EMERALD — as hex (`STATUS_HEX`: canvas markers in `MappedUnit`, `MapLegend`), Tailwind bundles (`STATUS_CHIP_CLASS`/`STATUS_DOT_CLASS`/`STATUS_INVERTED_CLASS`: `FieldStatusAtoms`, `MapSidebar`/`UnitInspector` stage dots), or inline pairs (`STATUS_INLINE`: the look-ahead `t.st.*` tokens). The palette is pinned by `statusColors.test.ts`; never hardcode a temporal-state color in a component. Out of scope on purpose: DB-sourced `status_logs.status_color` polygon fills, `VARIANCE_COLORS`, and the make-ready scale — those encode different information.
- **Map Lag Mode** (`mapSettings.colorByVariance`, toggled from `MapHorizontalToolbar`) recolors unit polygons by schedule variance. The recoloring happens **inside `FloorplanCanvas`** on copies of the bottleneck statuses (`displayStatuses` — the memo dispatches to pure `recolorForLag`/`recolorForMakeReady` in `src/utils/canvasRecolor.ts`, which never mutate their inputs) — never recolor `mapDisplayStatuses` in `page.tsx`, because that array feeds write paths (`BulkActionDock` bottlenecks, quick modals) and variance colors would be written to `status_logs.status_color`.
- **Dashboard scope:** `ProjectDashboard` always fetches all-project units/statuses/history; the per-level `FloorPulse` rail is both the rollup view and the scope control (it replaced the Active Level / All Levels toggle and the Active Locations / Not Started KPI cards). Forecasts are suppressed (not faked) for small samples and zero pace — keep that honesty if you touch `summarizeGroup`.

## 4. Best Practices
- Components needing client hooks must start with `"use client"`.
- If modifying database schemas, immediately reflect changes in the Supabase query definitions located in the hook files.
- **Database Schema Changes:** New tables (`status_audit_log`) and functions (`upsert_status_log`) must have their types added to `src/types/database.types.ts` (Tables and Functions blocks respectively). Derive domain types in `src/types/domain.ts` using `Database['public']['Tables']['<table>']['Row']`.
- **Location Taxonomy (`20260616_location_taxonomy.sql`):** A location (`units` row) carries a canonical `top_level_role` (`program`/`common`/`support`/`other`) and an optional `subtype_id` → the **global `subtypes` dictionary** (governed: `status` active/pending/deprecated, `aliases`, `default_project_types`); a project carries `project_type` (1 of 8). Source of truth for the constants + legacy mapping is `src/utils/locationTaxonomy.ts`; domain types (`Subtype`, `ProjectType`, `TopLevelRole`) and the JSONB guards (`isStringArray`, `isProjectTypeArray`) live in `domain.ts`. Invariants: (1) **`unit_type` is KEPT** — milestone applicability (`getAppliesTo`/`applies_to_unit_types`) still keys on it; the taxonomy is additive and not yet consumed by UI (Phase 3/4). (2) **`units.top_level_role` is the single source of truth for role** — NEVER derive a unit's role from its sub-type's role. (3) The legacy backfill mirrors `mapLegacyUnitType`'s **role** mapping; legacy types too generic for a specific sub-type were backfilled with `subtype_id = NULL` (not the `Other (pending)` sentinel), so the **review queue is `top_level_role IS NOT NULL AND subtype_id IS NULL`**. (4) `subtypes` **RLS: read = any authenticated member, write = `owner`/`admin`/`pm` only, never `anon`.**
- **Activity Dictionary (`20260702_activity_dictionary.sql`, Scheduling Foundation Slice A Phase 2):** a project activity (`activities` row) carries an optional `dictionary_id` → the **global `activity_dictionary`** — the scheduling twin of `subtypes`, MIRRORING it exactly (governed `status` active/pending/deprecated, JSONB `aliases` + `default_project_types`, globally-unique `name`, `Other (pending)` sentinel; plus `type` task/milestone, an optional default `track` hint, and a reserved `cost_code_id` for Slice B). Source of truth for the pure helpers (alias resolution/canonicalization, project-type ordering, the non-blocking propose→fields flow) is `src/utils/activityDictionary.ts`; domain types (`ActivityDictionaryEntry`, `ActivityDictionaryStatus`, `ActivityType`) live in `domain.ts` and reuse the existing `isStringArray`/`isProjectTypeArray` guards; the query/mutation hooks are `src/hooks/useActivityDictionary.ts` (mirror `useSubtypes.ts`). Invariants: (1) `activities.dictionary_id` is **additive + nullable** — the review queue is `dictionary_id IS NULL`; nothing is auto-linked. (2) It does **not** touch the Phase-1 status pipeline (`status_logs`/`activity_id` slot key, `upsert_status_log`, the audit trigger) — an activity's `track`/`color`/`sequence_order`/`applies_to_unit_types` stay project-local on `activities`; the dictionary only normalizes identity. (3) `activity_dictionary` **RLS: read = any authenticated member, write = `owner`/`admin`/`pm` only, never `anon`** (copied verbatim from `subtypes`).
- **Activity management lives in the Schedule view (Scheduling Foundation Slice A, Phase 3a):** the single home for building/sequencing a project's activities is `src/components/schedule/ActivityManagerPanel.tsx` (scopes of work, auto-advance, dictionary-backed add, drag-reorder, applies-to rules) inside `ScheduleWorkspace` — moved out of `SettingsMenu`, whose "Levels & Scopes" tab keeps ONLY sheet-scoped config (scope assignments + legacy scale preset). Do NOT regrow an activity editor in Settings (one home only). Level planned dates (`sheets.activity_schedules`) are owned by the Schedule view's `CascadePanel` and ALSO written by `MspImportPanel`'s anchor-loading (Unified Schedule Engine Phase 4) — both feed the same level-window engine (`cascadeLevelToLocations`/`reflowLevelToLocations` in `src/utils/ganttMath.ts`: crew-flow stagger via the importer's `subdivideTaskWindow`, provenance-aware re-flow that preserves hand-edits, FS chaining via `chainLevelSchedule` in `src/utils/dateRipple.ts` — all pure + tested, never forked).
- **Activity Dependencies (`20260703_activity_dependencies.sql`, Scheduling Foundation Slice A Phase 3b):** `activity_dependencies` holds light **Finish-to-Start** edges between a project's activities (`predecessor_activity_id`/`successor_activity_id` FKs → `activities(id)` `ON DELETE CASCADE`, `type` pinned to `'FS'` by CHECK, `lag_days` int — may be negative). **Coarse by design: no critical-path / float / resource-leveling math anywhere** (out of scope for Slice A — widen the CHECK additively if that ever changes). The table is pair-unique (a DAG stays possible) but the v1 UI authors ONE predecessor per activity via `useSetActivityPredecessor` (delete-then-insert replace); cycle prevention is app-level (`wouldCreateCycle` in `src/utils/activityDependencies.ts` — pure, tested). Hooks (`src/hooks/useActivityDependencies.ts`) are **online-first** (schedule authoring, never the offline queue). No `project_id` column — scope flows through the FKs; RLS read = member of the successor's project, write = `owner`/`admin`/`pm` (INSERT requires both endpoints in one project), never `anon`. Deleting an activity cascade-drops its edges — invalidate `queryKeys.activityDependencies(projectId)` alongside activities (see `handleDeleteActivity`).
- **MS Project import (Scheduling Foundation Slice A, Phase 4):** the Schedule view's `MspImportPanel` imports an MSPDI `.xml` export (P6 `.xer` / binary `.mpp` are out of scope), reconciles its tasks against the project's activities, and writes per-location planned dates. All correctness lives in two PURE modules (no I/O, no `Date.now()`, both unit-tested): `src/utils/mspImport.ts` (parser — drops `IsNull` spacers and `Active=0` tasks, derives each task's ancestor-summary `path` from `OutlineLevel`) and `src/utils/scheduleReconcile.ts` (exact→dictionary-alias→fuzzy matching via `resolveActivityByName`; "LEVEL n" sheet suggestion from name/path; task-window subdivision — area-weighted ONLY when every target unit has a positive `computed_area`, else an even split, never faked weights; `buildImportWrites` mirrors `cascadeLevelToLocations` exactly: non-destructive by default, N/A slots skipped, prior progress fields preserved). Invariants: (1) the bulk write goes ONLY through `useBulkInsertStatusLogs` (the chunked `.upsert` on `unit_id,activity_id`) — never plain `.insert()`, never the offline queue (online-first authoring, §2). (2) The write stays gated behind the explicit "N dates across M locations" two-step confirmation. (3) The import never touches `activity_dependencies` (dates-only v1). **Unified Schedule Engine Phase 4 additions:** the importer also (a) **anchor-loads** — confirmed task windows are written into each target sheet's `activity_schedules` (via `mergeLevelWindows` in `src/utils/scheduleBaseline.ts`; "All levels" rows skipped) so the Phase-3 re-flow's provenance test recognizes imported dates as plan-owned — and (b) **diffs against the newest schedule baseline** (per-task "new / ±Nd / = baseline" badges; accept/reject = the existing per-row include checkboxes).
- **Schedule baselines (`20260710_schedule_baselines.sql`, Unified Schedule Engine Phase 4):** `schedule_baselines` holds named, **immutable** whole-project snapshots of the schedule PLAN — JSONB `snapshot` = both layers (every sheet's level×activity windows + every dated slot's planned window), **never progress fields** (`temporal_state`/`logged_date`/`status_color` are excluded by contract, so nothing can "restore" progress from a baseline). Append-only by design: RLS has **NO UPDATE policy** (read = member, INSERT/DELETE = `owner`/`admin`/`pm`, never `anon`); fix a bad baseline by deleting + re-capturing, never editing. Narrow the JSONB at the query boundary with `isScheduleBaselineSnapshot` (domain.ts — a malformed snapshot degrades to "no baseline", never a crash). Pure capture/diff math lives in `src/utils/scheduleBaseline.ts` (`buildBaselineSnapshot`/`baselineDelta`/`mergeLevelWindows`/`resolveCurrentBaseline`, tested); hooks (`src/hooks/useScheduleBaselines.ts`) are **online-first** (schedule authoring, never the offline queue). The "current baseline" rule lives in ONE place — `resolveCurrentBaseline(baselines)` (Band vs Promise P3): the NEWEST captured baseline is the current one (no picker), degrading to null if its snapshot is malformed; never re-inline `baselines[0]`. Capture is first-class OUTSIDE the importer via `src/components/schedule/BaselineControl.tsx` (the Schedule-view header strip: honest "no baseline captured" empty state + a privileged owner/admin/pm capture button, reused inside `MspImportPanel`'s post-import nudge) — reuse it, don't fork another capture surface.
- Stick to Tailwind utilities for new implementations; do not introduce custom CSS files unless fundamentally required for Konva DOM overlays.

## 5. Hybrid Vector-Snapping Engine
- The backend parses CAD/PDF files via PyMuPDF into percentage-normalized line data.
- The frontend loads this array via `useSnappingVectors()` (which checks the `sheet_vectors` cache table first, then falls back to the backend API with write-through caching).
- **CRITICAL:** Do NOT attempt to persist instantiated `RBush` class objects into TanStack Query state, as this will crash the `@tanstack/react-query-persist-client` IndexedDB serialization. Always return raw JSON arrays from the hook, and instantiate `RBush` inside `useState` + deferred `useEffect(setTimeout(10))` blocks on the rendering side to avoid blocking the initial render — the canonical home is `src/hooks/useCanvasSnapping.ts` (the canvas's snapping engine, consumed by `FloorplanCanvas`).
- Rely on `getSnappedCoordinate()` in `src/utils/geometry.ts` for aspect-ratio aware mathematical snapping and "Gravity" corner-snapping. The `mixAlpha()` utility in the same file is the single source of truth for CSS color → rgba() conversion (handles hex, rgb, rgba inputs).
- **PDF Rendering (off-main-thread):** The floor-plan drawing is rendered client-side by pdf.js inside a dedicated Web Worker (`src/workers/pdfRender.worker.ts` + `src/workers/pdfRenderProtocol.ts`). `usePdfRenderer` is a thin client: it downloads the original PDF (through the module-level LRU byte cache in `src/utils/pdfByteCache.ts` — call `invalidatePdfBytes(sheetId)` whenever a sheet's original PDF changes) and receives transferred `ImageBitmap`s: a 1×/2× LOD pyramid eagerly, the 4× LOD lazily on first deep zoom, and debounced sharp viewport crops past `DEEP_ZOOM_THRESHOLD`. Shared pure math lives in `src/utils/pdfRenderMath.ts` (unit-tested). Do NOT call pdf.js `page.render` on the main thread — it rasterizes on the calling thread and janks Konva pan/zoom. PDF bytes and the preview PNG are fetched via **versioned public URLs** (`src/utils/pdfSource.ts`, `?v=<sheets.pdf_version>`) so the browser/CDN can cache them long-term; the backend bumps `pdf_version` on upload/re-attach. The server-rendered `converted/<sheetId>.png` doubles as an instant placeholder LOD before pdf.js output exists. The OpenSeadragon tile path was removed; `tile_manifest_url` is a vestigial column.

## 6. TypeScript Guardrails (CRITICAL)
- **Language:** This codebase is migrating incrementally from JavaScript to strict TypeScript. `tsconfig.json` has `allowJs: true` and `checkJs: false`, so `.js`/`.jsx` files remain valid during migration.
- **Type Registry:** All shared domain types live in `src/types/`. The single source of truth is `src/types/domain.ts`, which derives Row/Insert types from the auto-generated `src/types/database.types.ts`. **Never** hand-write a type that duplicates a Supabase table shape — always derive it via `Database['public']['Tables']['<table>']['Row']`.
- **JSONB Narrowing:** Supabase's type generator types JSONB columns as `Json`. You MUST narrow these at the query boundary (inside `queryFn`) using type guards or assertions — do NOT let `Json` propagate into component props. Use the `isPercentPointArray()` guard in `src/types/domain.ts` for `polygon_coordinates`.
- **IDB Serialization Safety:** The offline mutation queue (`src/utils/persister.ts`) uses `@tanstack/query-async-storage-persister` to write to IndexedDB. Every value flowing through TanStack Query cache MUST be JSON-serializable. **Never** store class instances (e.g., `RBush`, `Map`, `Set`, DOM nodes) in query state. If `JSON.parse(JSON.stringify(value))` would lose data, it cannot go in the cache.
- **Zustand Store Typing:** Every Zustand store must be created with an explicit state interface: `create<MyState>()(...)`. Setter functions that accept functional updaters must be typed as `(val: T | ((prev: T) => T)) => void`.
- **`pendingChanges` Remains Local:** The `pendingChanges` and `pendingTimelineChanges` state in `useFieldData.ts` is typed as `Record<string, PendingChange>` via local `useState`. This is intentional — do NOT migrate it to Zustand or TanStack Query. A separate IDB persistence layer (`src/utils/pendingChangesStore.ts`) persists these maps to IndexedDB using project-scoped keys via `idb-keyval`. Do NOT change the key format (`sitepulse-pending-changes-${projectId}`) or remove the `hasRehydrated` guard. Note: `setPendingTimelineChanges` is explicitly exported to allow `MobileSwipeDeck` to manage deep snapshot undo/redo queues. See Section 2 for full rationale.
- **No `any`:** Prefer `unknown` with type narrowing over `any`. During migration, `// @ts-nocheck` may be temporarily used on large files being converted, but must be removed before merging to main.
- **File Extensions:** New files must use `.ts`/`.tsx`. When converting an existing file, rename `.js` → `.ts` or `.jsx` → `.tsx` and fix all type errors before committing. Do not commit a renamed file that still has `// @ts-nocheck`  to the main branch.

## 7. Backend API Rules (`sitepulse-backend/main.py`)
- **Auth Pattern (CRITICAL):** ALL protected endpoints use `Depends(get_current_user)`. This dependency validates the Supabase user JWT **locally** with `PyJWT` and does NOT call `supabase.auth.get_user()`. Do NOT revert to that network call; it was a primary cause of `/extract-vectors` 500 timeouts on Render's free tier. This Supabase project signs user access tokens with an **asymmetric key (ES256)**, so verification uses the project's **JWKS public key**, NOT an HS256 shared secret (the old `SUPABASE_JWT_SECRET` value was actually the public key id — it can't, and must not, be used to verify: HS256 against a publicly-known value lets anyone forge a token). JWKS is fetched **once and cached** by `PyJWKClient` (module-level `_jwk_client`, `lifespan`), so steady-state verification still does no network I/O — the no-blocking-auth-call rule holds. Do NOT add an HS256 fallback unless a genuinely-secret HS256 key is configured. The correct pattern is:
  ```python
  import jwt  # PyJWT — NOT python-jose (abandoned, CVE-2024-33663)
  signing_key = _jwk_client.get_signing_key_from_jwt(token)   # cached JWKS lookup by kid
  payload = jwt.decode(token, signing_key.key, algorithms=["ES256", "RS256"], options={"verify_aud": False})
  ```
  `SUPABASE_JWT_SECRET` is now legacy/unused for verification (still read at startup; harmless). If Supabase is ever rotated back to HS256 signing, restore an HS256 branch guarded by a real secret.
- **Supabase Client Timeouts:** The global `supabase` client is initialized with `SafeClientOptions(postgrest_client_timeout=25, storage_client_timeout=25)`. `SafeClientOptions` is a local subclass of `ClientOptions` that adds the missing `storage` field — a guard against a supabase-py v2.28.3 regression where `_init_supabase_auth_client` reads `client_options.storage` but the dataclass omits it. Do NOT revert to plain `ClientOptions` unless a future supabase-py release restores the field. The 25-second limits exist to ensure storage downloads fail gracefully as catchable Python exceptions before Render's 30-second platform deadline fires an opaque process kill. Do NOT remove or increase these values without a corresponding Render plan upgrade.
- **Startup Validation:** The `lifespan` async context manager validates that `supabase.auth`, `supabase.storage`, and `supabase.postgrest` all initialized before accepting traffic. This converts silent import-time crashes into clear deploy-time failures in Render logs. Do NOT remove this guard.
- **No `python-jose`:** The project uses `PyJWT==x.x.x` exclusively. `python-jose` is abandoned (last release 2021, CVE-2024-33663) and must not be re-added.
- **No Debug File Writes:** Never write user data to disk in endpoint handlers (e.g., `open("debug.txt", "w")`). Render's filesystem is ephemeral and shared; this leaks PII. Use `print()` or structured logging to stdout only — Render captures stdout in its log dashboard.
- **Exception Handling:** Each endpoint wraps its work in `try / except fitz.FileDataError / except HTTPException / except Exception`. The `except fitz.FileDataError` branch returns a 404 (PDF not found). Storage timeouts surface as `httpx.ReadTimeout` and are caught by the generic `except Exception` block — they will now produce a descriptive 500 message instead of a silent platform kill.

## 8. Backend Dependency Notes (`sitepulse-backend/requirements.txt`)
- **`pyiceberg` is a transitive dependency of `storage3`** (the Supabase Storage client), which requires `pyiceberg>=0.10.0`. You cannot remove it from the installed environment by removing it from `requirements.txt` — pip's resolver will pull it back in. Do not waste effort attempting to eliminate it.
- **Do NOT manually pin `starlette`**: FastAPI manages its own compatible `starlette` version. A manual pin creates silent conflicts. Let FastAPI's declared dependency resolve it.
- **Do NOT re-add `python-jose`**: See §7. Use `PyJWT` only.
- **`rich`, `cachetools`, `tenacity`** are required by `supabase-py` internals. Keep them pinned even though `main.py` does not import them directly.
